Rapport Technique : Optimisation & Sécurité

Analyse des exigences 5 & 6

⚡ 1. Problèmes d'optimisation identifiés & Solutions

  • Index B-Tree manquants : Sans index sur (conversation_id, created_at), chaque récupération de messages nécessite un Full Table Scan O(N). Solution : Index composite ajouté pour une recherche en O(log N).
  • Problème N+1 requêtes : Récupérer les messages puis faire une requête par message pour chercher le pseudo de l'auteur génère N+1 allers-retours I/O. Solution : Jointure SQL unique INNER JOIN users ON messages.sender_id = users.id.
  • Gestion des verrous et I/O disque SQLite : Le mode par défaut bloque les lecteurs lors des écritures. Solution : Activation de PRAGMA journal_mode = WAL; (Write-Ahead Logging).
  • Consommation mémoire sur les gros historiques : Charger 100 000 messages d'un coup surcharge le serveur et le navigateur. Solution : Support de la pagination (LIMIT / OFFSET).

🔒 2. Problèmes de sécurité identifiés & Solutions

  • Injections SQL (CWE-89) : Concaténer les variables dans la commande SQL permettrait l'exécution de code arbitraire. Solution : 100% de requêtes préparées avec paramètres positionnels ?.
  • Failles Cross-Site Scripting (XSS - CWE-79) : Un utilisateur malveillant postant <script>alert(1)</script> pourrait pirater les sessions. Solution : Échappement HTML strict côté frontend avec textContent et encodage d'entités HTML.
  • Clés étrangères désactivées par défaut dans SQLite : Par défaut, SQLite accepte les messages orphelins (ID d'auteur ou salon inexistant). Solution : PRAGMA foreign_keys = ON; activé à chaque connexion.
  • Déni de service (DoS) par surcharge de charge utile : Envoi de chaînes gigantesques. Solution : Validation stricte des longueurs et types avec Pydantic côté backend.
